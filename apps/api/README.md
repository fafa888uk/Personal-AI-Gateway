# Personal AI Gateway — API (Stage B: core API gateway)

FastAPI gateway that proxies the official OpenAI API with a model
registry, client-key auth, rate/concurrency limits and hard budget stops.
Native Responses passthrough first; Chat Completions passthrough second.
No LiteLLM, no Open WebUI — first version is native passthrough only.

## Run locally

```bash
cd ~/workspace/personal-ai-gateway
python3 -m venv .venv
.venv/bin/pip install -r apps/api/requirements.txt
cp .env.example .env        # fill in values; .env is gitignored, never commit it
cd apps/api
../../.venv/bin/python -m gateway.seed_dev   # prints ONE test client key — save it
../../.venv/bin/python -m gateway.main       # uvicorn on 127.0.0.1:8000
```

Health check: `curl http://127.0.0.1:8000/api/health`

Local dev DB is SQLite at `data/dev.db` (gitignored, created automatically).
Production uses PostgreSQL + Alembic — see "Migrations" below.

## Model verification

All candidates start `pending` and are invisible to `/v1/models` and
uncallable. Verification is one real request per model:

```bash
curl -X POST http://127.0.0.1:8000/admin/models/gpt-5.4-mini/verify \
  -H "Authorization: Bearer $GATEWAY_ADMIN_KEY" \
  -H 'Content-Type: application/json' -d '{"mode": "real"}'
```

This sends a minimal `POST /v1/responses` (`input: "ping"`,
`max_output_tokens: 16`) with the production credential and records
`available` / `forbidden` / `unavailable` / `rate_limited` plus the
method (`real`) and time. It costs a tiny amount of API usage.
**Blocked until a real key exists** (returns 503 without one).

`{"mode": "mock"}` is a test-only path, allowed only when
`GATEWAY_ALLOW_MOCK_VERIFY=true`. It records
`verification_method: "mock-test-only"` and is never real verification.

## Budgets

Hard stops, checked before forwarding: global daily $5, global monthly
$50, per-client monthly $20 (defaults from env). Stage F: the global
limits can be overridden in the admin console (`PUT
/api/v1/admin/settings` → `system_settings`); the persisted values
win and env vars are the fallback. On hit, new requests get
HTTP 429 `budget_exceeded` and an audit event is recorded.

Costs come only from real upstream `usage` + a `pricing_rules` row.
- Upstream returned no usage → cost `not_obtained` (never exact).
- No price configured → cost `price_not_configured`, spend $0.
- Only `exact` costs count toward budgets. Until pricing is configured,
  budgets cannot trigger — configure pricing before relying on them.

## Admin console (Stage E: `/api/v1/admin/*`)

Cookie-session auth, separate from the bearer admin key (which keeps
working only on legacy `/admin/*` and never authenticates the new API):

- The single admin account is seeded once at startup from
  `ADMIN_USERNAME` + `ADMIN_PASSWORD` (Argon2id hash only; the table is
  left alone once non-empty). No password configured → login 503s.
- `POST /api/v1/admin/login` verifies Argon2id and sets an HttpOnly
  `SameSite=Lax` `pag_admin` cookie (12h by default, `Secure` when
  `SESSION_COOKIE_SECURE=true`). Wrong credentials → generic 401; more
  than 5 failed attempts per 15 minutes per (IP + username) → 429.
- Mutating requests must send `X-CSRF-Token` matching the session's
  token (from `GET /api/v1/admin/csrf`, also set as the `pag_csrf`
  cookie), else 403. GETs need only the session cookie.
- `GET /api/v1/admin/models` adds `in_upstream` (live upstream
  `GET /v1/models`) and `upstream_only`; `verification_status` comes
  only from the DB. `POST .../verify` reuses the legacy verify logic
  and warns that it sends a real request and may incur API cost;
  mock verification records `mock-test-only`, never `real`.
- Client-key list never shows raw key material (only `key_prefix`,
  first 12 chars at creation); create/regenerate return the raw key
  exactly once. `client_type` is `web | codex | vscode | other`.
- `GET /api/v1/admin/usage` aggregates all clients: request/success/
  error counts and rates, avg + p95 latency (null with no data),
  tokens, exact cost total with `exact / not_obtained /
  price_not_configured` breakdown (non-exact cost is never presented
  as exact), per-model and per-client rankings (by name, never raw
  key), daily trend, error distribution, and budget status with alerts.
- `PUT /api/v1/admin/settings` persists global budgets and
  `retention_days` in `system_settings` and upserts pricing rules;
  budgets must be ≥ 0, `retention_days` ≥ 1. Stage F: the persisted
  global budgets are now enforced on `/v1/*` calls too (env vars
  remain the defaults/fallback); legacy `GET /admin/budgets` still
  reports the env values.
- All admin changes (login/logout, failed logins, model/key/settings
  changes, verification, revoke/regenerate, password change, session
  revocation, backup creation) write an `audit_events` row.
- `POST /api/v1/admin/change-password` rotates the admin password
  (new password ≥ 12 chars, differs from the current one) and revokes
  every session; `POST /api/v1/admin/sessions/revoke-all` revokes
  every session without changing the password.

## Auth

- Client keys: `pag_sk_...`, stored only as SHA-256 hashes
  (`hmac.compare_digest`). Per-key allowed models (`["*"]` = any
  verified-enabled model), per-minute rate limit, concurrency limit,
  monthly budget, enabled/disabled. Raw key is shown exactly once.
- Admin key (`GATEWAY_ADMIN_KEY`) is a separate env secret; using it as
  a client key returns 401. It is never stored hashed in the DB.

## Forwarding rules (implemented)

- Unknown-but-legal params pass through untouched (structured outputs,
  tool calls, reasoning fields, image input preserved).
- SSE proxied byte-for-byte in order; client disconnect / cancel /
  timeout aborts the upstream request.
- Retry (max 2) with `Retry-After` + exponential backoff **only before
  streaming starts**; never after the first streamed byte.
- Real upstream status codes, request IDs and rate-limit headers are
  preserved; 401/403/404/429/5xx/network errors handled distinctly.
- Never silently downgrades models; incompatible requests get a clear
  error (`model_not_verified`, `model_not_allowed`, `model_incompatible`).
- Per-request internal trace ID (`X-Gateway-Trace-Id`) links the client
  call to the upstream request; logged in `api_request_logs`.
- Default logging stores no prompt content, API keys or sensitive tool
  params — only trace id, client, model, status, latency, tokens, error.

## Migrations

Production path is Alembic + PostgreSQL; migrations contain no
SQLite-only SQL:

```bash
cd apps/api
DATABASE_URL=postgresql+psycopg://gateway:PW@db:5432/gateway \
  ../../.venv/bin/alembic upgrade head
```

Local dev uses `Base.metadata.create_all` on startup (idempotent).

PostgreSQL needs a driver: `requirements.txt` includes
`psycopg[binary]>=3.2` (Stage F — it was missing before, so a
`postgresql://` engine failed to construct). Migrations
`0001 → 0002 → 0003` were verified against real PostgreSQL 16 locally
(2026-11-14, Stage F), including downgrade to 0002 and re-upgrade.

## Backup & restore (Stage F)

Full procedure + rehearsal evidence: `docs/BACKUP_RESTORE.md`.

- SQLite: `python3 scripts/backup_db.py backup|list|restore`
  (system python3 works — the CLI does not need the venv).
- PostgreSQL: `python3 scripts/backup_db.py pg-dump [--run]`;
  passwords travel via `PGPASSWORD`, never argv.
- Admin API: `GET /api/v1/admin/backups`,
  `POST /api/v1/admin/backups` (SQLite only; PostgreSQL → 501).
  Restore is CLI-only by design — never over HTTP onto a live DB.
- Backups are chmod 0600, manifest records SHA-256; retention by
  `retention_days` setting + `BACKUP_RETENTION_COUNT` env.

## Version endpoint

`GET /api/v1/app/version` (public, no auth — clients check for updates
before login) returns per-platform release info for the online-update
system:

```json
{"configured": true, "version": "1.0.0", "gateway_version": "0.3.0",
 "platforms": {"ios": {"version": "1.0.0", "release_date": "2026-11-14",
 "download_url": "https://github.com/fafa920q-hue/Personal-AI-Gateway/releases/download/v1.0.0/PersonalAI-1.0.0-ios-unsigned.ipa",
 "sha256": "<sha256>", "release_notes": "..."}, "windows": {}, "macos": {}, "web": {}}}
```

Data source is server-side only (`APP_VERSION` / `APP_RELEASE_INFO_JSON`
env). Unconfigured servers honestly return `{"configured": false,
"version": null, "platforms": {}}` — never fake release data. Clients
must never hardcode versions or embed a GitHub PAT. Release flow: tag a
GitHub Release first, then update the server's release info to match it.
