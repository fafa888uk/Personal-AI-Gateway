## 0. 第一原则（用户 2026-11-14 定）

**新服务器上独立运行一个私人 AI 平台：浏览器聊天、电脑上 Codex
编程、VS Code 里用 AI，全部接入同一套中转服务。以后新增模型，只需
在中转站里配置和验证一次，不必分别改造各个客户端。**

由此导出三条硬性设计规则：

1. **模型注册表 + 别名 + 权限是网关的中心能力。** 模型是否可见、
   可调用、默认是哪一个、别名指向谁，全部由网关的模型注册表决定。
2. **客户端只存 base URL 和自己的密钥，对模型无硬编码。**
   客户端配置示例（Codex / VS Code / 其他 OpenAI 兼容客户端）里
   不写死模型名；客户端调用时传的模型名由网关按注册表 + 别名解析、
   校验、授权。没有在注册表里、或未通过验证启用的模型，客户端
   看不到也调不到。
3. **新模型上线路径只有一条：网关配置 → 真实请求验证 → 启用。**
   验证通过前，模型不在 `/v1/models` 返回、不在聊天页模型列表出现、
   客户端调用返回明确错误（不可用/未验证），绝不显示为已验证成功。

## 1. 项目目标与边界

- 私人单管理员 AI 中转站：网页聊天、Codex CLI、VS Code Codex 扩展、
  其他 OpenAI 兼容客户端，共用同一网关。
- 完全独立：不对接 FAFA ONE，不读、不复制、不连接 FAFA ONE 或任何
  其他项目的代码、数据库、服务或凭证。
- 仅限个人使用：不做支付、充值、注册、分销。
- 上游唯一初始来源：OpenAI 官方 API。官方 API Key 只在服务端由
  环境变量注入，永不发给客户端。

## 2. 执行顺序（用户 2026-11-14 定，五条优先级）

1. **先完成 API 网关，再做网页美化。** 顺序：B 网关 → C Codex 真实
   端到端 → D 网页聊天先求功能可用 → 视觉精修放到最后。
2. **优先跑通真实 Codex 请求、工具调用和流式响应。** Codex CLI
   真实端到端工具调用是第一验收门槛，不过这一关，界面再漂亮也
   没有实际价值。网页聊天不得先于 Codex 验证去做美化。
3. **优先使用官方接口，不盲目转换协议。** 第一版以 OpenAI
   Responses 原生透传为主。可参考 LiteLLM 原生 Responses 透传和
   Open WebUI 兼容 API 的架构思路，但只是参考；第一版不安装大量
   用不到的组件，保持依赖最小。
4. **设置官方 API 费用上限，两层都要做**（见 §7）：
   - 服务器本地预算：全局每日/每月上限 + 每个客户端月度预算，
     到达即硬停 + 告警；默认先给保守值，等用户定数字。
   - 文档中写明并验证 OpenAI 官方项目侧的硬性费用限制设置方法，
     提醒用户去官方后台设置。
5. **先验证模型是否真的能调用。** 之前截图里的只是项目允许模型
   清单，不等于能调用。模型验证必须用将要正式使用的同一项目凭证
   发真实请求确认，截图清单不能算验证。真实密钥目前没有（严禁
   复用其他对话/截图里出现过的密钥，那些已泄露），所以真实模型
   验证和真实 Codex 测试记为明确阻塞项，等主聊天通过安全流程
   拿到用户提供的新密钥后再做；先用 Mock 上游完成全部本地测试，
   不得伪造验证结果。

## 4. 核心网关（阶段 B）

端点（第一版，Responses 原生透传优先）：

- `GET /v1/models` — 只返回注册表中已验证启用的模型（含别名解析后
  的规范名）；未验证模型不出现。
- `POST /v1/responses` — 原生透传，保留结构化输出、工具调用、
  reasoning 相关字段；支持流式 SSE 与非流式。
- `POST /v1/chat/completions` — OpenAI 兼容透传。
- Responses 相关查询/取消/压缩端点：按真实 Codex 版本实际需求验证
  后按需支持（`GET /v1/responses/{id}`、取消、压缩等），不凭猜测
  实现不存在的端点。

转发规则（全部强制）：

- 上游地址固定配置，客户端不得指定目标 URL（SSRF 防护）。
- 客户端鉴权（Bearer 客户端密钥）→ 模型权限校验 → 速率限制 →
  预算检查 → 上游转发。
- 未知但合法的模型参数原样透传；不重写、不删除工具调用、图片
  输入、结构化内容等重要字段。
- 正确代理 SSE 流式响应，保留事件顺序和必要响应头；客户端断开、
  取消、超时要正确处理并终止上游请求。
- 保留真实上游 HTTP 状态码、请求 ID、速率限制与错误类型；对
  401/403/404/429/5xx/网络错误分别处理。
- 有限重试：仅在未开始流式返回前，按 `Retry-After` + 指数退避；
  已开始流式返回后绝不重试（防重复执行工具、重复扣费）。
- 禁止默认把高能力模型切换成低能力模型；不兼容的请求返回明确
  错误，不伪造成功。
- 每个请求生成内部追踪 ID，关联客户端调用与上游请求；默认不记录
  完整 Prompt、API Key、工具调用敏感参数或隐私数据。

候选模型（仅为配置清单，**无一视为已验证可调用**）：

`gpt-5.4-mini-2026-03-17`、`gpt-5.4-nano-2026-03-17`、

注册表字段：规范名、别名、启用/停用、默认模型标记、手动排序、
固定版本单独归类、能力标记（Responses / Chat / 流式 / 工具调用 /
图片输入）、验证状态（待检测 / 可用 / 不可用 / 权限不足 / 速率受限）、
最后验证时间与验证方式。

验证规则：

- 必须用将要正式使用的同一项目凭证发真实请求确认；截图清单、
  模型名推测、历史记录都不能算验证。
- 未通过实际验证的模型不能显示为已验证成功；不得凭模型名称推测
  上下文窗口、定价或支持能力。
- 手动单模型测试必须真实发送请求，并明确提示可能产生 API 费用。
- 验证状态变化记入审计事件。

## 7. 费用上限（两层，强制）

本地预算（服务器侧硬停，默认保守值，等用户定数字）：

| 预算 | 默认值 | 行为 |
|---|---|---|
| 全局每日上限 | 5 USD | 到达即拒绝新请求（明确错误 + 告警） |
| 全局每月上限 | 50 USD | 同上 |
| 每客户端每月预算 | 20 USD | 同上（按客户端） |

- 费用按上游实际返回 usage 计；上游未返回精确 usage 时标记为
  未获取/估算，绝不显示为精确用量；价格未配置时显示“价格未配置”。
- 预算状态要可查询、可告警（日志 + 管理页提示）；到达上限是硬停，
  不是软提示；管理员可调，但调整记入审计。
- 官方项目侧：文档（`docs/OPENAI_BUDGET.md`）必须写明并验证在
  OpenAI 官方后台设置项目硬性费用限制的方法（按官方最新界面核实，
  不凭记忆写死路径），并提醒用户务必设置，因为 Codex 自动执行可能
  连续发大量请求，本地预算只是第二道防线。

## 9. 安全与数据

- 单管理员，不开放注册；Argon2id；Secure HttpOnly SameSite Cookie；
  登录失败次数限制；CSRF；API Key 最小权限；HTTPS 强制；生产严格
  CORS；密钥只从环境变量或安全密钥文件加载；`.env` 永不提交；
  敏感日志脱敏；SQL 注入与 SSRF 防护；请求大小限制；容器最小权限；
  PostgreSQL 不暴露公网；关闭不必要端口；管理接口单独鉴权。
- 数据实体：`admin_accounts`、`admin_sessions`、
  `upstream_providers`、`model_registry`、`client_keys`、
  `chat_sessions`、`chat_messages`、`api_request_logs`、
  `usage_records`、`pricing_rules`、`system_settings`、
  `audit_events`。Alembic 迁移、索引、数据保留与清理策略；对话内容
  是否保存可配置，默认优先保护隐私。
- 管理后台（阶段 E 已实现，见 STATUS.md）：单管理员账号（Argon2id，
  启动时从 `ADMIN_USERNAME` + `ADMIN_PASSWORD` 种子）+ 会话 Cookie
  （HttpOnly SameSite=Lax，12h）+ 双提交 CSRF + 登录失败限流（5 次 /
  15 分钟）；规范管理 API `/api/v1/admin/*`（模型/密钥/用量/诊断/
  设置/审计）；旧 bearer `/admin/*` 保留兼容。Web 管理控制台
  `apps/web/src/app/admin/*` 通过 `src/lib/admin.ts` 调用；该文件集中
  归一化后端响应信封（嵌套 capabilities/tokens、per_*/pricing_rules、
  `{id}` upstream 条目、cost 明细对象）为页面用的平铺形状——后端与
  前端字段名不一致时只改归一化层，不改后端 API。【2026-11-14 阶段 F
  已交付】持久化到 `system_settings` 的全局预算已接入 `/v1/*` 请求
  时强制（环境变量仍为默认值/兜底）；管理后台新增改密、全部会话撤销、
  备份清单/创建接口；日志脱敏 + 轮转；备份与恢复脚本 + 两次真实恢复
  演练（SQLite 与 PostgreSQL，见 `docs/BACKUP_RESTORE.md`）；安全自查
  见 `docs/SECURITY.md`。
- 备份与恢复脚本 + 真实恢复演练（有证据的演练记录）。

  回滚）+ Web/PWA 客户端随服务端更新自动获得新版；流程写进运维文档
  并真实演练一次。

## 13. 服务端职责（用户 2026-11-14 定，全部由服务端承担）

新服务器承担六件事：**统一 API 中转、模型管理、历史聊天、设备同步、
客户端鉴权、更新信息**。客户端只做展示与输入，不自带服务端能力。

### 13.1 历史聊天与设备同步（阶段 C 已实现 v1 契约）

- 历史聊天存在服务端：`chat_sessions` / `chat_messages` 表
  （migration `0002_chat_history`，阶段 C 落地）+ 客户端密钥隔离
  的接口（见下）。`api_request_logs` 仍不存 prompt 内容；消息内容
  只存在 `chat_messages` 里（同步存储本身，可按会话删除）。
- v1 接口（全部要客户端密钥，只能看到自己的会话，别人的返回 404）：
  `POST /api/v1/chats`、`GET /api/v1/chats`（按 `updated_at` 倒序）、
  `GET /api/v1/chats/{id}`、`PATCH /api/v1/chats/{id}`（改名/改模型）、
  `DELETE /api/v1/chats/{id}`（服务端硬删除）、
  `GET /api/v1/chats/{id}/messages`、
  `POST /api/v1/chats/{id}/messages`（role/content/model/tokens）。
  另有 `GET /api/v1/usage/summary?period=today|month`（仅调用方密钥
  的服务端汇总，cost_status 如实报告）。
- v1 同步方式：**服务端为准，全量拉取**——客户端打开会话列表与
  下拉刷新时调 `GET /api/v1/chats` 拿全量；新建/改名/删除/消息写
  入都直接调服务端接口，成功后刷新列表。同一账号在各端看到同一份
  记录（服务端同一份数据）。
- **未实现（不得谎称已有）**：增量同步（按时间戳拉变化）、删除
  tombstone、离线缓存/草稿/待发送队列。当前离线时客户端无法同步，
  删除为硬删除。以上随网页聊天（阶段 D）或后续阶段再补，补之前
  文档保持这个口径。
- 同一管理员账号登录即同步；不同设备不共享官方 Key（见 §13.3）。

### 13.2 更新信息接口

- 服务端提供版本信息接口 **`GET /api/v1/app/version`**，返回各平台
  实际可用的版本信息：版本号、发布日期、下载地址、SHA-256、更新说明。
  桌面/移动客户端检测新版本时查此接口，不要写死在客户端里；客户端
  不允许内置 GitHub PAT，通过服务端安全获取发布信息和受控下载地址。
- 版本信息的数据源在服务端（发版时更新的服务端配置），未配置任何
  发布时接口明确返回“未配置发布”，不得伪造版本号或下载地址。
- GitHub Releases 是下载源，服务端是信息源，两者版本号必须一致；
  发版流程：先打 GitHub Release，再更新服务端版本信息；不一致时
  客户端以服务端信息为准并明确提示。

### 13.3 客户端鉴权

- 仍按原计划走服务端：独立客户端密钥 + 作用域（允许模型、速率、
  预算），设备本身不存官方 Key；管理员密钥绝不兼作客户端密钥。

## 14. 技术路线与 CI / 发版工作流（用户 2026-11-14 定）

- **Flutter**：iOS、Windows、macOS 三端客户端，界面和功能代码
  尽量共用一套（`apps/flutter`）。
- **Next.js**：网页聊天和管理后台（`apps/web`）。
- **FastAPI**：独立 AI API 中转服务（`apps/api`）。
- **PostgreSQL**：同步聊天记录、设置与用量。
- **GitHub Actions**：自动编译 IPA、EXE、DMG，以及服务端镜像。
- **GitHub Releases**：集中发布各平台安装包。
- **Docker Compose + Caddy**：新服务器部署和 HTTPS。

工作流目标：以后 Codex 更新一次源码，就通过 GitHub 工作流分别
生成各平台安装包；网页和服务器在测试通过后部署更新，移动和桌面端
从 Releases 获取对应版本。

CI 流程：

1. 一次 push 触发：服务端镜像构建 + 三端包构建（macOS runner 出
   IPA/DMG，Windows runner 出 EXE）。
2. 测试全过才进 Releases；任一测试失败不得发版。
3. 版本号单点管理：仓库内唯一版本源（`VERSION` 文件 / 发布 tag），
   服务端版本信息接口（`GET /api/v1/app/version`）与 Releases 版本一致；
   不一致时客户端以服务端信息为准并明确提示。
4. Flutter 客户端在网关和网页聊天可用之后再接（阶段顺序不变），
   不得先做客户端美化。
